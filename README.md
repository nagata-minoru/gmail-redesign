# gmail-redesign

手書きスケッチを出発点にした、Gmail モバイル UI の再設計コンセプトです。メールを「見つける・読む・返信する」という基本操作に集中できるよう、画面構成と操作の優先順位を見直します。

> ダミーデータで動く Web プロトタイプを[公開](https://nagata-minoru.github.io/gmail-redesign/)していますが、実際のメールは扱えません。Google の公式機能ではありません。

## 概要

既存のメール体験では、情報や操作が一画面に集まりやすく、重要なメールの発見や本文の閲覧に集中しにくい場面があります。本プロジェクトでは、モバイルでの利用を前提に、情報の強弱、直接操作、読みやすい余白を軸として Gmail の体験を再考します。

## 目標と設計原則

- **重要な情報を先に見せる**: 送信者、件名、アラート、日時などを整理し、優先度を素早く判断できるようにする。
- **よく使う操作を近くに置く**: スター、返信、転送、スワイプ操作を、画面遷移を増やさず実行できるようにする。
- **読むことを邪魔しない**: メール本文に集中できる、整理されたヘッダーと十分な余白を設ける。
- **状態を分かりやすく伝える**: 通知、空の受信トレイ、検索結果なしなどの状態を、言葉と視覚表現で明確にする。
- **ライト／ダークの両方で見やすくする**: 警告色、HTML メール、文字のコントラストをそれぞれのテーマで検討する。

## 想定する画面

### 1. 受信トレイ

- 検索、メニュー、アカウントへの入口を上部に集約
- 「すべて／未読／スター付き／添付ファイル」のタブで一覧を絞り込む案
- 送信者、件名、本文の冒頭、日時、スターを一覧で見やすく表示
- 未読メールは送信者名の前に印（●）を付けて区別する案
- 重要なセキュリティ通知などは、警告アイコン、「アラート」ラベル、背景色で目立たせる案
- 一覧からスターを直接切り替える
- 行を左にスワイプするとアーカイブ操作が現れる案
- 右下の作成ボタンから新規メッセージを開始

### 2. メール詳細

- 件名、送信者、受信日時を分かりやすく配置し、件名の横にスターを置く
- 戻る、アーカイブ、削除、未読、その他の操作を上部のツールバーに整理
- 返信、全員に返信、転送を画面下部にまとめて置く
- 下部の絵文字ボタンから短い反応を返す、絵文字リアクションの可能性を検討
- 本文を読みやすくし、ダークモードでの HTML メール表示も検討

### 3. メール作成

- 宛先、差出人、件名、本文を迷わず入力できる構成
- 宛先はチップで表示し、個別に削除・追加できるようにする
- 差出人欄に送信元アカウントを常に表示し、そこから切り替えられるようにする
- 添付、画像、絵文字、書式、送信の操作をキーボードのすぐ上に配置
- 日本語キーボード表示時にも本文と主要操作を確認できるレイアウトを検討

## 主なアイデア

| テーマ | 構想 |
| --- | --- |
| スター | 一覧と詳細の両方から、メールを開かずに近い感覚で素早く切り替える。 |
| スワイプ操作 | アーカイブや既読などの頻繁な処理を、一覧から直接行えるようにする。 |
| 重要度とアラート | セキュリティ通知などを識別しやすく表示し、ライト／ダーク両テーマで視認性を確保する。 |
| ダークモード | 文字、警告色、HTML メールのコントラストと読みやすさを検討する。 |
| Empty State | 受信トレイや検索結果が空のとき、状態を説明するメッセージと親しみやすいイラストを表示する。 |
| 絵文字リアクション | 返信文を書くほどではない短い反応を、軽く返せる可能性を探る。 |
| アカウント切り替え | 閲覧中・作成中ともに、どのアカウントを使っているかを明確にする。 |
| Gmail と Meet | メールと会議の行き来を自然にする連携を、探索的なテーマとして検討する。 |

## 現在のステータス

このリポジトリは、手書きスケッチを整理した **UI コンセプト／ローファイワイヤーフレーム** と、ダミーデータで動く **Web プロトタイプ** です。

### 実装済み（Web プロトタイプ）

- 受信トレイ：検索、絞り込みタブ（すべて／未読／スター付き／添付ファイル）、未読の印、アラート行、スターの切り替え、左スワイプでアーカイブ、検索結果なしと空の受信トレイの Empty State
- メール詳細：開くと既読、アーカイブ・削除・未読にする、スター、返信・全員に返信・転送、絵文字リアクション（試作）
- メール作成：宛先のチップ入力と形式チェック、差出人アカウントの切り替え、返信・転送時の件名と引用、入力中に閉じるときの破棄確認
- アーカイブ・削除の結果を画面下部に表示し、「元に戻す」で取り消せる
- ライト／ダークテーマ（端末の設定に従う）
- 受信トレイの上端に、非公式のコンセプトでデータはダミーであることを示す注記
- ローカルでの Gmail 読み取り（Web のみ・読み取り専用）：受信トレイ上部の帯の「Gmail を読む」で接続し、受信トレイの新しい 20 件を表示する（[Gmail を読む](#gmail-を読むローカル開発)）。同意画面は初回だけで、再読み込み後は 1 回押すだけでつながる。帯の「詳細」またはアカウントのアイコンで、権限の説明と接続の解除を開く。接続中は注記が「実際の受信トレイを読み取り専用で表示中」に変わり、スター・アーカイブ・削除・未読・リアクションは Gmail に反映されない旨を通知して画面も変えない

ダミーデータ版の Web プロトタイプを GitHub Pages で公開しています: <https://nagata-minoru.github.io/gmail-redesign/>。Gmail 連携の開発に入ったため、この公開サイトは更新を止めており、ダミーデータ版の最後の状態のままです。

データはメモリ上のダミーだけで、ページを再読み込みすると初期状態に戻ります。送信もデモで、実際にはどこにも送られません。

## 技術構成と開発

| 項目 | 内容 |
| --- | --- |
| フロントエンド | [Expo](https://expo.dev/)（React Native、Expo Router）。同じコードを Web と iOS／Android で動かせる |
| 公開先 | GitHub Pages（`/gmail-redesign/` 以下。Gmail 連携の開発中は自動公開を止め、手動実行のみ）と Cloudflare Workers の静的アセット配信（`wrangler.jsonc`） |
| テスト | Node 標準のテスト（`node --test`）。画面に依存しない関数（Gmail 応答の変換、絞り込み・検索、宛先の形式チェック、返信・転送の初期値、取り消しでの並び順の復元）とダミーデータを検証する |
| E2E テスト | [Playwright](https://playwright.dev/)（Chromium、Pixel 7 の画面サイズ）。書き出した Web 版を実際にブラウザで操作し、絞り込み・検索、メール詳細、アーカイブと取り消し、メール作成（宛先の形式チェック、差出人の切り替え、破棄の確認、返信）を確認する |
| CI | GitHub Actions で型チェック・lint・テスト・Web ビルド・E2E テストを順に実行。依存パッケージ・Web ビルドの変換結果・E2E 用のブラウザはキャッシュして実行時間を短くする（`.github/workflows/ci.yml`） |
| バックエンド | 現在はなし。通知などが必要になった段階で Ruby で用意する予定（Cloudflare 以外に配置） |

```sh
npm install          # 依存パッケージを入れる
npm run web          # 開発サーバを起動してブラウザで開く
npm run typecheck    # 型チェック
npm run lint         # ESLint
npm test             # テスト（src/ 以下の *.test.ts）
npm run test:e2e     # Web 版を書き出して E2E テスト（初回は npx playwright install chromium が必要）
npm run build:web    # dist/ に静的ファイルを書き出す（ルートで配信する場合）
npm run build:pages  # GitHub Pages 向けに、/gmail-redesign/ 以下で動くよう書き出す
npm run deploy       # 書き出して Cloudflare に公開する（wrangler へのログインが必要）
```

配信するパスは、ビルド時の環境変数 `WEB_BASE_URL` で切り替えます（`app.config.ts`）。GitHub Pages への公開は `.github/workflows/pages.yml` が行いますが、Gmail 連携の開発中は `main` への push では動かず、手動実行のみです。

### Gmail を読む（ローカル開発）

Google Identity Services のトークン方式で、ブラウザだけで完結します。サーバーもクライアントシークレットも使いません。

- 権限は `gmail.readonly` のみ。アクセストークンはタブのメモリにだけ保持し、`localStorage`・Cookie・ファイルには保存しません。リフレッシュトークンも使いません。タブを閉じるか「接続を解除」で消え、解除時は Google 側でも失効させます。
- 保存するのは公開してよい OAuth クライアント ID だけです（`.env.local`。Git には入りません）。
- 画面には本文を文字列としてだけ出し、HTML メールは描画しません。
- 自動テストは実際の Google にも実メールにも接続しません（作り物のデータだけ）。

手順（Google Cloud での設定はご自身で行ってください）:

1. Google Cloud Console でプロジェクトを作り、Gmail API を有効にする
2. OAuth 同意画面を「テスト」状態で作り、テストユーザーに自分のアカウントを追加する
3. 「ウェブ アプリケーション」の OAuth クライアント ID を作り、承認済みの JavaScript 生成元に `http://localhost:8081` を追加する
4. `.env.example` を `.env.local` にコピーし、`EXPO_PUBLIC_GOOGLE_CLIENT_ID` にクライアント ID を入れる
5. `npm run web` で起動し、受信トレイ上部の帯の「Gmail を読む」を押す

トークンを保存しないため、ページを再読み込みすると接続は切れます。もう一度「Gmail を読む」を押してください（同意済みならポップアップはすぐ閉じます）。

`npm run build:web`（E2E・Cloudflare・GitHub Pages 向けの書き出し）は `.env.local` を読みません（`EXPO_NO_DOTENV=1`）。公開する版にはクライアント ID が入らず、接続の帯も出ません。

画面のコードは `src/app/`（`index.tsx` が受信トレイ、`mail/[id].tsx` がメール詳細、`compose.tsx` がメール作成）、ダミーデータは `src/data/mails.ts` にあります。画面に依存しない処理は `src/lib/` に置き、テストを隣に置いています。E2E テストは `e2e/` にあります。スワイプ操作、ダークテーマの見た目、iOS／Android 実機での動作のテストは未整備です。
